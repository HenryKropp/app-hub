# MCP do Ziv, Etapa 1 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a person's Claude (claude.ai/desktop via OAuth, Claude Code via a personal code) find apps and artifacts, run apps and publish artifacts in the Ziv, acting as that person.

**Architecture:**
- The MCP server lives inside each company's Go `Handler`, at `/mcp` (company path `/w/<slug>/mcp`), on streamable HTTP via `github.com/modelcontextprotocol/go-sdk` v1.8.0.
- Tools never reimplement rules. Each tool calls the existing JSON handlers in-process (`h.api.ServeHTTP` on an internal request) with the person's identity in the request context, so access rules, validation and Portuguese error messages come out exactly as in the screens.
- A small OAuth 2.1 authorization server (discovery metadata, dynamic client registration, PKCE S256, refresh rotation) and personal codes both produce rows in one `mcp_connections` table.

**Tech Stack:** Go stdlib `net/http`, pgx/sqlc, go-sdk `mcp` package; React + TS + Tailwind/shadcn; Vitest.

**Spec:** `docs/superpowers/specs/2026-11-04-mcp-design.md`

## Global Constraints

- MCP endpoint per company: principal `<origin>/mcp`, others `<origin>/w/<slug>/mcp`. A token from one company never works in another (each company has its own schema, so its own tables).
- Tokens: `ziv_` + 32 random bytes base64url; stored only as SHA-256 hex; shown once; never logged.
- OAuth lifetimes: authorization request 10 min, authorization code 60 s and single use, access token 1 h, refresh token 30 days and rotated on every use. Personal codes have no expiry and live until cancelled.
- Revoking a connection, or deleting the person (cascade), makes the next MCP call return 401. Logging out of the web does not touch MCP connections.
- No tool response contains vault values, secret config, shared-app env values or tokens.
- Tool names, descriptions and messages are in simple Brazilian Portuguese. The product is "o Ziv".
- Rodar and Publicar are tools with `readOnlyHint: false`. Every other tool has `readOnlyHint: true`.
- Things that come in through MCP are marked: `artifacts.origin = 'mcp'` (already allowed by migration 016) and the new `runs.origin = 'mcp'`. The UI says "pelo Claude".
- Frontend: neutral look per `DESIGN.md`; coral only on run actions.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Backend tests: `cd backend && set -a && . ../.env && set +a && mise x -- go test ./...`. Frontend: `cd frontend && mise x -- npx vitest run && mise x -- npx tsc -b`.

## Review Focus

1. **A token used against another company's address** (`/w/teste/mcp` with a principal token) gets 401, not that person's data. The test lives in Task 2.
2. **A cancelled or expired token on the very next call** gets 401 with `WWW-Authenticate` pointing to the metadata. There is no grace cache. Tests in Task 2 and Task 3.
3. **An app the person cannot see:** `buscar` omits it, and `rodar_app`/`ver_app` return the handler's own 403/404 text as a tool error (`isError: true`), never a Go error or a panic. Test in Task 4.
4. **Rodar with no computer connected:** the tool error carries "Seu computador não está conectado." plus the next step (open the Agente). Test in Task 4.
5. **OAuth edge cases:** a wrong PKCE verifier, a reused code, a `redirect_uri` that differs from the registered one, or a non-https non-localhost redirect at registration each give `invalid_grant`/`invalid_request` and never issue a token. Tests in Task 3.

**Interfaces:**
- Consumes: Task 1 `mcpConnection`, `withMCPPerson`, `h.api`.
- Produces:
  - `func (h *Handler) mcpHTTP() http.Handler`: wraps the go-sdk `mcp.NewStreamableHTTPHandler`. It is stateless (`Stateless: true`) and checks the bearer token before the SDK runs.
  - On a missing or invalid token it answers 401 with `WWW-Authenticate: Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource<basePath>/mcp"`.
  - On success, the person ID lives in the request context, and tools read it via `func mcpPersonFrom(ctx) int64`.
  - `func (h *Handler) callAPI(ctx context.Context, method, path string, body any) (status int, raw []byte)`: builds an internal request carrying `withMCPPerson`, serves it with `h.api`, and returns the status and body.
  - `func apiError(raw []byte) string`: pulls the `error` text out of the JSON.
  - Server name `ziv`. `Instructions` is a short Portuguese paragraph saying what the Ziv is and that the tools act as the person.
  - Routing:
    - Portal forwards `rest == "/mcp"`, `strings.HasPrefix(rest, "/oauth/")` and `strings.HasPrefix(rest, "/.well-known/")` to the company handler, exactly like `/api/`.
    - At the root, Portal also maps `/.well-known/<name>/w/<slug>/<tail>` to company `slug` with `rest = "/.well-known/<name>/<tail>"` (tail may be empty). `<name>` is `oauth-protected-resource` or `oauth-authorization-server`.
    - `Secure` skips the Origin, Sec-Fetch and JSON-only checks for `/mcp`, `/oauth/token` and `/oauth/register`. Those endpoints are bearer- or PKCE-protected, not cookie-authenticated.
  - Vite proxy adds `'/mcp'`, `'/oauth'` and `'/.well-known'`, and extends the company regex to `^/w/[^/]+/(api/|auth/|up$|mcp$|oauth/|\.well-known/)`.

### Task 3: OAuth for claude.ai and the Claude app

**Files:**
- Create: `backend/internal/handler/mcp_oauth.go`, `backend/internal/handler/mcp_oauth_test.go`

**Interfaces:**
- Consumes: Tasks 1–2.
- Produces (all relative to the company base; `issuer` = `cfg.BaseURL`):
  - `GET /.well-known/oauth-protected-resource/mcp` and `GET /.well-known/oauth-protected-resource`: return `{resource: issuer+"/mcp", authorization_servers: [issuer], bearer_methods_supported: ["header"]}`.
  - `GET /.well-known/oauth-authorization-server`: returns `{issuer, authorization_endpoint: issuer+"/oauth/authorize", token_endpoint: issuer+"/oauth/token", registration_endpoint: issuer+"/oauth/register", response_types_supported: ["code"], grant_types_supported: ["authorization_code","refresh_token"], code_challenge_methods_supported: ["S256"], token_endpoint_auth_methods_supported: ["none"]}`.
  - `POST /oauth/register` (RFC 7591, JSON):
    - accepts `{client_name, redirect_uris}`;
    - every URI must be `https://…` or `http://localhost[:port]/…` / `http://127.0.0.1[:port]/…`, otherwise 400 `invalid_redirect_uri`;
    - returns 201 `{client_id, client_name, redirect_uris, token_endpoint_auth_method: "none"}`.
  - `GET /oauth/authorize`:
    - validates `response_type=code`, the client, a `redirect_uri` among those registered, and `code_challenge_method=S256`;
    - a bad client or redirect gets a plain Portuguese 400 page with no redirect;
    - on success it stores an `mcp_auth_requests` row and 302s to `<basePath>/conectar-claude/autorizar?pedido=<id>`.
  - Cookie-authenticated consent API:
    - `GET /api/oauth/requests/{id}` returns `{client_name, redirect_host}`, or 404 when missing or expired;
    - `POST /api/oauth/requests/{id}/approve` returns `{redirect: "<redirect_uri>?code=<code>&state=<state>"}`;
    - `POST /api/oauth/requests/{id}/deny` returns `{redirect: "<redirect_uri>?error=access_denied&state=<state>"}`.
  - `POST /oauth/token` (`application/x-www-form-urlencoded`):
    - `grant_type=authorization_code` takes `code`, `redirect_uri`, `client_id` and `code_verifier`, checked with `base64url(sha256(verifier)) == challenge`. It consumes the code and creates an `mcp_connections` row with `kind='oauth'` and `name=client_name`.
    - `grant_type=refresh_token` rotates both hashes.
    - The response is `{access_token, token_type: "Bearer", expires_in: 3600, refresh_token}`.
    - Errors use RFC 6749 JSON: `invalid_grant`, `invalid_request`, `unsupported_grant_type`.
