# Home Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new first page (`/`), the Home. For everyone it has "Meu dia": warnings, starred apps and artifacts, recently used items and the latest runs. For admins and area leaders it adds "Meu time". The catalog moves to `/apps`.

**Architecture:**
- Two new per-company tables: `favorites` (a star a person put on an app or an artifact) and `artifact_opens` (one row per opening, for "used").
- Two read endpoints, `GET /api/home` and `GET /api/home/team`, build the page from existing data (runs, computers, shared apps, Admin's approval state) plus the new tables. Every item goes through the access rules that already exist (`acc.For` and `acc.ForArtifact`).
- A star toggle goes on cards and on the app and artifact pages. A new `HomePage` sits at `/`, and the catalog moves to `/apps`.

**Tech Stack:** Go net/http, pgx, sqlc, React/Vite/TS, shadcn/ui, Vitest, Playwright (screenshots).

**Spec:** `docs/superpowers/specs/2026-11-03-home-e-artifacts-design.md`, section 5 (and section 3: sections with no content disappear; "Meu time" only for those who lead). Artifacts (sections 4 and 6) are already shipped: ADR 018, commits 81788b2 and 84ec2cc.

## Global Constraints

- All UI text is in Brazilian Portuguese, in plain language. The style follows ADR 008, using `components/bits.tsx` and `components/ui`. Follow the look of `ArtifactsPage.tsx` and `AdminPage.tsx`.
- Add new migrations only (`018_home.sql`); never edit an old one. Every table lives inside each company's schema.
- New SQL goes in `backend/internal/database/queries/home.sql` (sqlc). After `sqlc generate`, keep only the generated files for the queries you touched and `models.go`, and revert any unrelated churn with `git checkout`. Admin's raw-SQL `collect` helper is not used for new queries. `h.adminApps(ctx)` may be called as it is.
- Every item the Home shows (favorite, recent, warning, team news) passes the item's access check: `acc.For(...)` for apps, `acc.ForArtifact(...)` for artifacts. Something the person cannot see never appears, and its name never leaks.
- Fixed numbers from the spec:

  | Number | Meaning |
  |---|---|
  | 5 minutes | a run stuck waiting for the computer |
  | 7 days | warning window |
  | 6 | items in "Usados recentemente" |
  | 30 days | recent window |
  | 5 | latest runs |
  | 7 days | "Quem está usando" |
  | 14 days | "O que estão criando" |

- Scope of "Meu time":
  - A person with the `manage_roles` permission sees the whole company.
  - Otherwise, someone who leads one or more areas sees the people (members and leaders) and the items of those areas, added together.
  - Anyone else gets 404, and the UI hides the section.
- "Pendências de gestão" appear only for the `manage_people` permission, and always cover the whole company.
- Empty parts disappear (spec §3). The only exception is "Favoritos", which shows one short line explaining the star.
- Handler tests need `set -a && . ./.env && set +a` (DATABASE_URL). Never start a test server on port 8080.

## Plan rulings (cofounder's choices, to be confirmed in plan review)

1. **"App com ponto de atenção"** = an app the person cares for (owner, backup or area leader) with at least one run **with an error, by anyone, in the last 7 days**. The ficha's "Pontos de atenção" are fixed notes, so using them would leave the warning box always full for every owner.
2. **"Apps e artifacts sem responsável ativo"** is left out. Today the Ziv cannot deactivate or remove a person, so an owner is always active and this list would always be empty. It comes back when "desativar pessoa" exists. This is recorded in ADR 019.
3. **Opening an artifact** is recorded when its detail is loaded (`GET /api/artifacts/{id}`), at most once every 30 minutes per person and artifact. Saving or editing does not count.
4. **Invitations not accepted** = not accepted and not revoked. Expired ones show the mark "venceu". Pending access requests (`membership_requests` with status `pending`) also appear under "Pendências de gestão".
5. **The run warning can be dismissed** on the Home itself through the existing `POST /api/runs/{id}/dismiss` ("Dispensar"). Other warnings go away when their cause is solved.
6. **No computer, no computer warning:** a person who has never connected a computer gets no warning. "Começar" already covers that case.

### Task 2: `GET /api/home` ("Meu dia")

**Files:**
- Create: `backend/internal/handler/home.go`
- Modify:
  - `backend/internal/database/queries/home.sql`
  - `backend/internal/handler/handler.go` (route)
- Test: `backend/internal/handler/home_test.go`

**Interfaces:**
- Consumes `ListFavorites` and `artifact_opens` from Task 1. It also uses these existing pieces:
  - `ListApps` and `ListArtifacts`, used to resolve and filter items.
  - `ListRuns` with `person_id = me`, `app_ids = []` and `lim = 5`.
  - `ListPersonComputers`, plus `agentproto.Version`.
  - `h.sharedBriefs(r)`, which can return nil.
  - `h.adminApps(ctx)` together with `h.securityConfig(ctx)`, but only when `h.workspace != nil`.
- Produces these new sqlc queries:
  - `ListMyAttentionRuns(person_id)`: runs with `dismissed_at IS NULL` and `created_at > now()-7 days`, where either `status='error'` or (`status='waiting'` and `created_at < now()-5 minutes`). It returns id, app_id, app_name, status, created_at and error_message, newest first, with a limit of 10.
  - `CountAppErrorsSince(since)`: app_id and count of `status='error'` runs with `created_at > since`, grouped by app.
  - `ListMyRecentApps(person_id)`: app_id and `max(created_at)` of my runs in the last 30 days.
  - `ListMyRecentArtifacts(person_id)`: artifact_id and `max(opened_at)` of my openings in the last 30 days.
- Produces the route `GET /api/home` → 200 with this JSON:

```ts
type HomeItem = { kind: "app" | "artifact"; id: number; name: string; summary: string; area: string; used_at?: string }
type HomeWarning = {
  kind: "run_error" | "run_waiting" | "computer_offline" | "agent_outdated" | "shared_crashed" | "app_errors" | "approval_pending"
  at: string                 // when it happened (run created, last seen, status changed, now)
  app_id?: number; app_name?: string; run_id?: number
  computer_name?: string; count?: number
}
type Home = { attention: HomeWarning[]; favorites: HomeItem[]; recent: HomeItem[]; runs: RunRow[] } // RunRow = existing ListRuns row JSON
```

- Warning rules (only for the person asking, and only on items they can view):
  - `run_error` / `run_waiting`: from `ListMyAttentionRuns`.
  - `computer_offline`:
    - Applies only when the person has at least one non-revoked computer and none of them is connected.
    - Produces one warning, for the computer seen most recently (`computer_name`, with `at` set to its `last_seen_at`).
  - `agent_outdated`: one warning per non-revoked computer whose `agent_version` is not empty and differs from `agentproto.Version`.
  - The warnings below go to the apps the person **cares for**: `OwnerID == me`, or `BackupID == me`, or `acc.Leads[AreaID]`.
    - `shared_crashed`: the shared status is `crashed`.
    - `app_errors`: the app has at least 1 error run in 7 days, and `count` holds how many (ruling 1).
    - `approval_pending`: applies only when the workspace exists and `RequireApproval` is on. The app has `!Approved && !Suspended` in `adminApps`.
  - Order: run warnings first (newest first), then computer warnings, then app warnings by name.
- `favorites`: in `ListFavorites` order, dropping anything missing or not viewable.
- `recent`: apps and artifacts merged and sorted by `used_at` (newest first), without favorites, viewable only, at most 6.

**Interfaces:**

- Produces sqlc queries. Each takes `all_areas bool` and `area_ids bigint[]`, and the scope filter reads `(sqlc.arg(all_areas)::bool OR … = ANY(sqlc.arg(area_ids)::bigint[]))`:
  - `TeamPeople`: the people in scope. For `all_areas`, that is everyone. Otherwise, it is the members and leaders of `area_ids`. It returns id and name.
  - `TeamUsage(person_ids bigint[])`:
    - Columns: `person_id`, `runs_7d` and `opens_7d`.
    - Also `ever_used` (true when the person has any run or any opening).
    - A leader's view counts only runs of apps in the led areas and openings of artifacts in the led areas.
  - `TeamCreations`: the union of two sources, both in scope and within the last 14 days.
    - App events: `apps.created_at`, with event `created`, and `app_versions` with `number > 1`, with event `new_version`.
    - Artifact events: the same, from `artifacts` and `artifact_versions`.
    - Each row carries kind, id, name, area_id, owner_id, backup_id, restricted, person_name, event, version and at. It is ordered by `at DESC` with a limit of 30.
  - `ListPendingInvitations`: rows with `accepted_at IS NULL AND revoked_at IS NULL`, giving id, email, created_at and `expires_at < now()` as `expired`.
  - `ListPendingRequests`: id, name, email and created_at where `status='pending'`.
  - `ListPeopleWithoutArea`: people with no row in either `area_members` or `area_leaders`.
- Produces the route `GET /api/home/team` → 200 with the JSON below, or 404 "Não encontrado." for someone without `manage_roles` and without led areas.

```ts
type TeamHome = {
  scope: "company" | "areas"; areas: string[]           // names of led areas when scope = "areas"
  usage: { person_id: number; name: string; runs_7d: number; opens_7d: number }[]   // only people with runs_7d+opens_7d > 0, most active first
  never_used: { person_id: number; name: string }[]
  creating: { kind: "app" | "artifact"; id: number; name: string; person_name: string; event: "created" | "new_version"; version: number; at: string }[]  // viewable items only, max 20
  pending: null | {                                       // null unless manage_people
    invitations: { id: number; email: string; created_at: string; expired: boolean }[]
    requests: { id: number; name: string; email: string; created_at: string }[]
    without_area: { id: number; name: string }[]
  }
}
```
